## 1. ภาพรวม — ทำอะไร ทำไมต้องมี

### โปรเจกต์นี้ทำอะไร

**Shabu Mood** คือระบบจัดการหน้าร้านสำหรับร้านชาบู/หมูกระทะบุฟเฟต์ ครอบตั้งแต่ลูกค้ายืนรอหน้าร้านจนพนักงานเก็บโต๊ะเสร็จ แบ่งเป็น 4 ฝั่งที่ใช้ฐานข้อมูลก้อนเดียวกัน

| ฝั่ง | ใครใช้ | เข้าทางไหน |
|---|---|---|
| ลูกค้า | คนที่นั่งโต๊ะ | สแกน QR บนสลิป ไม่ต้องสมัครสมาชิก |
| พนักงานหน้าร้าน + ครัว | พนักงาน | ล็อกอินอีเมล/รหัสผ่าน |
| ผู้จัดการ | เจ้าของร้าน / ผู้จัดการ | ล็อกอิน แล้วต้องมี role `owner` หรือ `manager` |
| จอคิวหน้าร้าน | เปิดค้างบนทีวี | ล็อกอินบัญชีพนักงานแล้วเปิดทิ้งไว้ |

### ทำไมถึงสร้างระบบนี้

ตรวจพบจาก `docs/presentation-brief.md` และ `docs/product-plan.md`

- โจทย์เป็น **ร้านสมมติ** อ้างอิงรูปแบบธุรกิจจากร้านบุฟเฟต์ชาบูทั่วไป
- แรงจูงใจตั้งต้นคืออยากทำ **ระบบจัดคิวหน้าร้าน** แล้วขยายเป็นระบบเต็มวงจร
- เป็นงานส่งวิชา **31900-1002 การจัดการฐานข้อมูลขนาดใหญ่**

### จุดที่ทำให้ฐานข้อมูลนี้ “ไม่เหมือนร้านอาหารทั่วไป” — ประโยคเปิดที่ควรพูด

ร้านทั่วไปคิดเงิน **ต่อจาน** ราคาจึงอยู่ที่ `order_items` แต่บุฟเฟต์คิดเงิน **ต่อหัว × แพ็กเกจ**

ผลต่อการออกแบบคือ

1. `order_items` ของอาหารในบุฟเฟต์ถูกบังคับให้ราคาเป็น 0 ด้วย CHECK constraint ที่ระดับฐานข้อมูล
2. ยอดบิลจึงประกอบขึ้นจาก 3 แหล่ง — จำนวนคน × ราคาแพ็กเกจใน `visits` + `visit_addons` + เฉพาะรายการที่ไม่รวมในบุฟเฟต์
3. เวลานั่งกลายเป็นข้อมูลที่ต้องบังคับ (90 หรือ 120 นาทีตามแพ็กเกจ) ไม่ใช่แค่ข้อความเตือน

**หลักฐานในโค้ด** — `supabase/migrations/0006_orders.sql`

```sql
constraint chk_order_item_buffet_price check (
  (is_buffet_included and unit_price_satang = 0 and line_total_satang = 0)
  or (not is_buffet_included and line_total_satang = unit_price_satang * quantity)
)
```

### หลัก 4 ข้อที่ยึดทั้งฐานข้อมูล

เขียนไว้หัวไฟล์ `supabase/migrations/0001_extensions_enums.sql` บรรทัด 5–10 — ท่องให้ได้ เป็นคำตอบสำเร็จรูปของคำถามหลายข้อ

1. **เงินเก็บเป็นสตางค์ (integer) เสมอ** คอลัมน์ลงท้าย `_satang` ห้ามใช้ float
2. **ราคาและอัตราทุกตัวมาจากตารางตั้งค่า** ไม่ hardcode ในโค้ด
3. **กฎธุรกิจบังคับที่ชั้นฐานข้อมูล** ด้วย constraint + trigger + RPC ไม่ใช่แค่ใน UI
4. **เวลาใช้ `timestamptz` เสมอ** แสดงผลตาม timezone ใน `restaurant_settings`

## 2. ใครทำอะไร (หลักฐานจาก Git)

### สิ่งที่ Git บอกได้

ตรวจด้วย `git shortlog -sne --all` — พบ **identity เพียงชุดเดียว**

| ชื่อที่ปรากฏ | อีเมล | จำนวน commit |
|---|---|---|
| `Admin` | `jarnballproject@gmail.com` | 39 |
| `jarnballproject-ops` | `jarnballproject@gmail.com` | 4 |

**อีเมลเดียวกันทั้งหมด** ชื่อที่ต่างกันสองชื่อเป็นการตั้งค่า git config คนละเครื่อง/คนละบริบท (ชื่อ `-ops` ปรากฏเฉพาะบน merge commit ของ Pull Request ซึ่งเป็น commit ที่ GitHub สร้างให้) ไม่ใช่คนละคน

**สรุปตามหลักฐาน:** โปรเจกต์นี้ทำคนเดียว ทุกส่วนตั้งแต่ออกแบบ schema, เขียน migration + RPC, frontend ทั้ง 4 ฝั่ง, เขียนเทสต์ และเอกสาร

> ถ้าถูกถามว่า “ทำกันกี่คน” ตอบได้เต็มปากว่าคนเดียว และมีหลักฐานเปิดให้ดูได้ทันทีด้วย `git shortlog -sne`
> ถ้าความจริงคือทำเป็นกลุ่ม — **Git ระบุไม่ได้** เพราะทุก commit มาจากบัญชีเดียว ต้องไปถามสมาชิกในทีมเอง เอกสารนี้ยืนยันแทนไม่ได้

### โครงสร้าง branch ที่ใช้จริง

```
main                              ← สายหลัก
feat/queue-ticket-and-qr-ordering ← สายงานฟีเจอร์ รวมกลับผ่าน Pull Request #1 และ #2
```

Workflow ที่ตรวจพบคือ **GitHub Flow แบบย่อ** — แตกสาขาฟีเจอร์ ทำงาน แล้ว merge กลับ `main` ผ่าน PR ไม่มี `develop` ไม่มี release branch

## 4. User Flow

### เส้นทางหลัก 7 ขั้น (ใช้เป็นสคริปต์เดโม)

```
1. ออกบัตรคิว        พนักงาน /staff/queue      → queue_tickets + daily_counters
2. เรียกคิว          พนักงานกดเรียก             → จอ /display ขยับเองภายในไม่กี่วินาที
3. จัดโต๊ะ/เปิดรอบ    เลือกโต๊ะ + แพ็กเกจ + จำนวนคน → visits (snapshot ราคา) + tables=occupied
4. ลูกค้าสแกน QR      มือถือลูกค้า /v/:token      → visit_devices ผูกเครื่องเข้ากับโต๊ะ
5. สั่งอาหาร          /order/menu                → orders + order_items → จอครัวเด้งทันที
6. ครัวทำ/เสิร์ฟ      /staff/kds → /staff/serve   → order_items เดินสถานะรายจาน
7. เช็คบิล/ชำระ/ปิด   /staff/checkout            → bill_lines + payments → visit=paid → closed
8. เก็บโต๊ะ           กดเก็บโต๊ะ                  → tables: cleaning → available
```

### เส้นทางสำรองที่ต้องรู้ว่ามี

- **QR สติกเกอร์ติดโต๊ะ + รหัส 6 หลักบนสลิป** — ใช้เมื่อลูกค้าทำสลิปหาย หรือเพื่อนมาทีหลัง
- **ทางเข้าด้วย token ล้วน** (`0010_token_fallback.sql`) — เผื่อกรณีเปิด Anonymous sign-in ไม่ได้ แลกกับการไม่มี Realtime ต้อง poll แทน ตรวจพบว่ามีฟังก์ชันครบ 4 ตัวแต่ **หน้าเว็บปัจจุบันยังไม่ได้เรียกใช้** (frontend เรียก `join_visit` / `join_visit_with_code` เท่านั้น)

## 5. Tech Stack — ทีละตัว พร้อมเหตุผลและทางเลือกอื่น

ตรวจจาก `frontend/package.json`, `supabase/tests/package.json`, `e2e/package.json`

### 5.1 PostgreSQL (ผ่าน Supabase)

| หัวข้อ | เนื้อหา |
|---|---|
| **ใช้ทำอะไร** | เก็บข้อมูลทั้งหมด **และเป็นที่อยู่ของตรรกะธุรกิจทั้งระบบ** — 42 ฟังก์ชัน 26 trigger 54 RLS policy 61 CHECK constraint 57 foreign key |
| **ทำงานอย่างไร** | frontend ไม่เขียนตารางตรง แต่เรียก stored procedure (RPC) ฟังก์ชันตรวจสิทธิ์ ตรวจกฎ ล็อกแถวด้วย `FOR UPDATE` แล้วค่อยเขียน ทุกอย่างในหนึ่ง transaction |
| **ทำไมถึงเลือก** | ระบบร้านอาหารมีข้อมูลที่ผิดไม่ได้คือเรื่องเงิน จึงต้องการฐานข้อมูลที่ **บังคับความถูกต้องได้ด้วยตัวเอง** ไม่ฝากไว้กับโค้ดหน้าเว็บที่ผู้ใช้แก้ได้ |
| **ใช้แทนได้ด้วย** | MySQL · MongoDB · SQLite · Firebase Firestore |
| **ข้อดี** | ACID transaction · FK บังคับความสัมพันธ์ · ENUM เป็น type จริง · `jsonb` สำหรับ audit log · **Row Level Security** ซึ่งเป็นตัวที่ทำให้ระบบนี้ไม่ต้องมี backend แยก |
| **ข้อเสีย** | ตรรกะอยู่ใน SQL ทำให้ทดสอบยากกว่าโค้ดภาษาโปรแกรมทั่วไป · คนในทีมต้องอ่าน PL/pgSQL เป็น · ย้ายไปฐานข้อมูลอื่นทีหลังแพงมาก |
| **ถ้าเปลี่ยนเป็น MySQL** | เสีย RLS ไปทั้งหมด → ต้องเขียน backend server มาเป็นด่านแทน · `jsonb` ใน audit log ต้องเปลี่ยนเป็น JSON แบบ query ยากกว่า · ENUM ของ MySQL เป็น string ที่ผูกกับคอลัมน์ ไม่ใช่ type ที่ใช้ซ้ำได้ |
| **ถ้าเปลี่ยนเป็น MongoDB** | ไม่มี FK → มีโอกาสเกิดออเดอร์ที่ชี้ไปโต๊ะที่ไม่มีอยู่จริง · ไม่มี CHECK constraint → กฎ “ของในบุฟเฟต์ราคาต้องเป็น 0” ต้องไปเขียนในแอป · transaction ข้าม collection ทำได้แต่ไม่ใช่ทางถนัด ขณะที่ `close_visit` แก้ 5 ตารางพร้อมกัน |
| **ถ้าเปลี่ยนเป็น SQLite** | เขียนพร้อมกันหลายคนไม่ได้เพราะล็อกทั้งไฟล์ แต่ร้านชาบูมีพนักงานกดพร้อมกันตลอดเวลา — ตกตั้งแต่ข้อนี้ |

**คำถามที่อาจารย์น่าจะถาม:** “ทำไมไม่ใช้ MongoDB ในเมื่อเมนูมีโครงสร้างไม่ตายตัว”
**คำตอบ:** ส่วนที่ไม่ตายตัวจริง ๆ ในระบบนี้มีแค่ `tags` ของเมนูกับ `provider_payload` ของการชำระเงิน ซึ่ง PostgreSQL รองรับด้วย `text[]` และ `jsonb` อยู่แล้ว แต่ส่วนที่เหลือคือเรื่องเงินและสิทธิ์ ซึ่งต้องการความเข้มงวดที่ MongoDB ไม่ได้ให้ — เลือกฐานข้อมูลตามส่วนที่ผิดไม่ได้ ไม่ใช่ตามส่วนที่ยืดหยุ่น

### 5.2 Supabase (Backend-as-a-Service)

| หัวข้อ | เนื้อหา |
|---|---|
| **ใช้ทำอะไร** | ให้ 4 อย่างพร้อมกัน — PostgreSQL ตัวจริง · PostgREST (REST API อัตโนมัติจาก schema) · Auth (อีเมล/รหัสผ่าน + anonymous) · Realtime (WebSocket ส่งการเปลี่ยนแปลงของตาราง) · Storage (เก็บรูปเมนู) |

| **ทำไมถึงเลือก** | ทำคนเดียวในเวลาจำกัด ถ้าเขียน backend เองต้องทำ REST + Auth + WebSocket เองทั้งหมด และที่สำคัญกว่าคือ Supabase เป็น **PostgreSQL ตัวจริง ไม่ใช่ของเลียนแบบ** ทำให้ยังใช้ RLS, trigger และ stored procedure ได้เต็มที่ |
| **ใช้แทนได้ด้วย** | Firebase · AWS Amplify · เขียน Express/NestJS + Postgres เอง · PocketBase |
| **ข้อดี** | ลดงานที่ไม่ใช่แก่นของวิชาลงมาก · ไม่ต้องดูแลเซิร์ฟเวอร์ · Realtime มาพร้อมและผูกกับ RLS เดียวกัน |
| **ข้อเสีย** | **ผูกติดกับผู้ให้บริการ** (vendor lock-in) ในส่วน Auth และ Realtime · project ฟรีจะ “หลับ” เมื่อไม่มีคนใช้ ต้องปลุกก่อนเดโม · ปรับจูน performance ระดับลึกทำได้จำกัด |
| **ถ้าเปลี่ยนเป็น Firebase** | Firestore เป็น NoSQL → ต้องรื้อ schema ทั้งหมด · ไม่มี SQL, ไม่มี transaction ข้ามหลายตารางแบบที่ `close_visit` ต้องใช้ · Security Rules ทำแทน RLS ได้บางส่วนแต่เขียนกฎที่ join ข้าม collection ไม่ได้ |
| **ถ้าเขียน backend เอง (Express/NestJS)** | ได้อิสระเต็มที่และย้ายผู้ให้บริการง่ายขึ้น แต่ต้องเขียนกฎ “ห้ามเก็บเงินเกินยอดบิล” ซ้ำทุก endpoint และต้องทำ WebSocket เอง — งานเพิ่มขึ้นหลายเท่าโดยได้ความถูกต้องเท่าเดิม |

### 5.3 Row Level Security (RLS) — ตัวชูโรงของโปรเจกต์

| หัวข้อ | เนื้อหา |
|---|---|
| **ใช้ทำอะไร** | เขียนกฎสิทธิ์ **ติดไว้กับตาราง** ไม่ใช่ติดไว้กับโค้ดแอป — 54 policy บน schema `public` + 4 policy บน `storage.objects` |
| **ทำงานอย่างไร** | ทุก query ที่วิ่งเข้าตารางจะถูก PostgreSQL เติมเงื่อนไขของ policy ต่อท้ายให้อัตโนมัติ ผู้ใช้ 2 ชนิดแยกด้วย helper function 2 ตัว |
| **ตัวอย่างจริง** | `create policy read_own_visit on visits for select to authenticated using (is_staff() or id = current_visit_id());` — ลูกค้าเห็นได้เฉพาะรอบของตัวเอง โดยไม่ต้องมีโค้ดแอปมาช่วยกรองเลย |
| **ทำไมถึงเลือก** | เพราะ endpoint ถูกยิงตรงได้เสมอ กฎที่อยู่แค่ใน UI ข้ามได้หมดด้วย DevTools หรือ `curl` |
| **ใช้แทนได้ด้วย** | ตรวจสิทธิ์ใน backend middleware · ทำ view แยกต่อ role · ตรวจใน frontend (ไม่ปลอดภัย) |
| **ข้อดี** | กฎมีที่เดียว ทุกทางเข้าถูกบังคับเหมือนกัน · เพิ่มแอปมือถือทีหลังไม่ต้องเขียนกฎใหม่ |
| **ข้อเสีย** | **RLS จำกัดได้เป็น “แถว” ไม่ใช่ “คอลัมน์”** — เป็นเหตุผลที่ปุ่ม “ของหมด” ต้องทำเป็น RPC แยก (`set_menu_item_availability`) ไม่งั้นให้สิทธิ์ UPDATE แล้วพนักงานจะแก้ราคาได้ด้วย · policy ซับซ้อนมีต้นทุน query · debug ยากเพราะ “ไม่เห็นข้อมูล” กับ “ไม่มีข้อมูล” หน้าตาเหมือนกัน |
| **ถ้าไม่ใช้ RLS เลย** | ต้องมี backend server เป็นด่านเดียว แล้วปิดไม่ให้ใครยิงฐานข้อมูลตรง — เปลี่ยนสถาปัตยกรรมทั้งระบบ |

**สองด่านที่ต้องท่องให้ได้**

```sql
is_staff()    -- มีแถวใน profiles และ is_active = true
is_manager()  -- เหมือนข้างบน และ role อยู่ใน ('owner','manager')
```

### 5.5 State Management — React Context + useReducer (ไม่ใช่ Redux)

> **ข้อควรระวังก่อนพูด:** `package.json` มี `@reduxjs/toolkit` และ `react-redux` ติดตั้งอยู่ แต่ **ตรวจแล้วไม่มีไฟล์ไหนใน `frontend/src` import เลยสักบรรทัด** (โฟลเดอร์ `src/redux/` มีแต่ `.gitkeep`)
> **ห้ามพูดว่า “ใช้ Redux”** ถ้าอาจารย์เปิดโค้ดดูจะเจอทันที ให้ตอบว่าเคยตั้งใจใช้ตอนวางโครง แล้วไม่ได้ใช้จริง เพราะ Context + useReducer เพียงพอ และยังลบ dependency นี้ทิ้งไม่ทัน

| หัวข้อ | เนื้อหา |
|---|---|
| **ของจริงที่ใช้** | `frontend/src/context/StoreProvider.jsx` — 822 บรรทัด ใช้ `createContext` + `useReducer` + `useCallback` |
| **ทำงานอย่างไร** | มี state ก้อนเดียวครอบทั้งแอป หน้าจอทุกหน้าเรียก `useStore()` แล้ว `dispatch(action)` เหมือนกันหมด ตัว `dispatch` เป็นคนตัดสินว่าจะยิง RPC จริงหรือแก้ state จำลอง |
| **จุดออกแบบที่น่าพูด** | รองรับ **2 โหมด** โดยหน้าจอไม่ต้องรู้ว่าอยู่โหมดไหน — `live` (ต่อฐานข้อมูลจริง) กับ `demo` (ใช้ข้อมูลจำลองใน `data/demo.js` เมื่อยังไม่ได้ติดตั้ง schema) ทำให้เปิดดูหน้าจอได้ก่อนมีฐานข้อมูล |
| **ทำไมไม่ใช้ Redux** | Redux ให้ประโยชน์เมื่อมี state ที่ซับซ้อนหลายก้อนและต้องการ time-travel debugging ระบบนี้มี state ก้อนเดียวและ **ความจริงอยู่ที่ฐานข้อมูล** ไม่ใช่ที่เบราว์เซอร์ — เพิ่ม Redux เข้ามาจะได้ boilerplate เพิ่มโดยไม่ได้อะไรกลับ |
| **ใช้แทนได้ด้วย** | Redux Toolkit · Zustand · Jotai · TanStack Query (เหมาะที่สุดในทางทฤษฎี เพราะ state ส่วนใหญ่เป็น server state) |
| **ข้อเสียของทางที่เลือก** | ไฟล์เดียว 822 บรรทัด ใหญ่เกินไป · ทุกครั้งที่ state เปลี่ยน component ที่ใช้ `useStore()` จะ re-render หมด ซึ่ง Redux/Zustand มี selector ช่วยลดตรงนี้ได้ |
| **ถ้าเปลี่ยนเป็น TanStack Query** | จะได้ cache, retry, และการ invalidate ที่เขียนเองอยู่ตอนนี้แบบฟรี ๆ — เป็นคำตอบที่ดีสำหรับคำถาม “ถ้าทำใหม่จะเปลี่ยนอะไร” |

### 5.6 API Layer — PostgREST + RPC (ไม่ได้เขียน backend เอง)

| หัวข้อ | เนื้อหา |
|---|---|
| **ใช้ทำอะไร** | **อ่าน** ผ่าน PostgREST แบบ `select` ธรรมดา · **เขียน** ผ่าน RPC (stored procedure) 21 ตัว |
| **กฎที่ยึด** | `frontend/src/api/mutations.js` บรรทัดแรก — “เรียก RPC ทั้งหมด ไม่ INSERT/UPDATE ตรงเข้าตาราง” เพราะเขียนตรงเข้าตารางจะข้ามการตรวจเวลา เพดานการสั่ง การล็อกแพ็กเกจ และการกันจ่ายเกินไปทั้งหมด |
| **ข้อยกเว้นที่ตรวจพบ** | หน้าผู้จัดการ (`api/admin.js`) เขียนตรงเข้าตารางได้ เพราะ policy ชุด `manage_*` เปิดให้เฉพาะ `is_manager()` อยู่แล้ว — กฎยังอยู่ที่ฐานข้อมูลเหมือนเดิม ส่วนที่แตะเงินหรือสถานะยังต้องผ่าน RPC |
| **ข้อมูลส่งอย่างไร** | HTTPS · `POST /rest/v1/rpc/<ชื่อฟังก์ชัน>` body เป็น JSON · header มี `apikey` (anon key) และ `Authorization: Bearer <JWT>` |
| **ทำไมเลือกแบบนี้** | ได้ REST API ครบโดยไม่ต้องเขียน และ **กฎธุรกิจถูกบังคับที่เดียว** ไม่ว่าจะเข้ามาทางหน้าเว็บ มือถือ หรือ `curl` |
| **ใช้แทนได้ด้วย** | REST API เขียนเอง · GraphQL · gRPC |
| **ข้อเสีย** | URL ของ API ผูกกับชื่อตาราง/ฟังก์ชัน เปลี่ยนชื่อแล้วหน้าเว็บพัง · ไม่มีที่วาง business logic ที่ไม่เกี่ยวกับฐานข้อมูล เช่นการส่งอีเมล |
| **ถ้าเปลี่ยนเป็น GraphQL** | ได้ข้อดีคือหน้าจอขอเฉพาะฟิลด์ที่ต้องการ ลดข้อมูลที่ส่งเปล่า แต่ต้องมี resolver layer เพิ่มและยังต้องพึ่ง RLS เหมือนเดิม — งานเพิ่มโดยที่ปัญหาหลัก (ความถูกต้องของเงิน) ไม่ได้ดีขึ้น |

**RPC ทั้ง 21 ตัวที่หน้าเว็บเรียกจริง** (ยืนยันด้วยการ grep `rpc('` ทั้ง `frontend/src`)

`issue_queue_ticket` `call_queue_ticket` `cancel_queue_ticket` `get_queue_status` `open_visit` `join_visit` `join_visit_with_code` `adjust_visit_guests` `place_order` `advance_order_item` `set_menu_item_availability` `apply_promotion_code` `remove_visit_promotion` `request_visit_bill` `visit_amount_due` `create_payment` `confirm_payment` `cancel_payment` `close_visit` `mark_table_clean` `void_visit`

> ฐานข้อมูลมี 42 ฟังก์ชัน แต่หน้าเว็บเรียกแค่ 21 ตัว ที่เหลือเป็น helper ภายใน (`is_staff`, `next_counter`, `log_audit`) trigger function และทางเข้าสำรองที่ยังไม่ได้ใช้ — **ตอบได้เลยถ้าถูกถามว่าทำไมตัวเลขไม่ตรงกัน**

### 5.7 Supabase Realtime

| หัวข้อ | เนื้อหา |
|---|---|
| **ใช้ทำอะไร** | ทำให้ทุกจอเห็นตรงกันโดยไม่ต้องกดรีเฟรช — ลูกค้าสั่ง → จอครัวเด้ง · ครัวกดพร้อมเสิร์ฟ → ลูกค้าเห็นสถานะเปลี่ยน · เปิด/ปิดโต๊ะ → ผังโต๊ะและจอคิวอัปเดต |
| **ทำงานอย่างไร** | WebSocket ฟัง `postgres_changes` ของตารางใน publication `supabase_realtime` ตรวจพบว่ามี **8 ตาราง** — `visits` `orders` `order_items` `service_requests` `tables` `queue_tickets` `payments` `menu_items` |
| **จุดที่ต้องพูดให้ได้** | `frontend/src/api/realtime.js` หน่วง event ไว้ 180 มิลลิวินาทีแล้วรวมกันโหลดรอบเดียว เพราะการสั่งอาหาร 1 รอบทำให้เกิด event หลายตัวติดกัน (1 order + N order_items) ไม่ควรโหลดใหม่ทุก event |
| **ข้อจำกัดสำคัญที่ออกแบบรับมือไว้** | **Realtime ส่ง event DELETE โดยไม่กรองด้วย RLS** (payload มีแค่ primary key) schema นี้จึง **ใช้การเปลี่ยน status แทนการลบแถวเสมอ** — เป็นเหตุผลที่ยกเลิกคิวแล้วยังเก็บแถวไว้เป็น `cancelled`/`no_show` |
| **ใช้แทนได้ด้วย** | Polling ทุก N วินาที · Server-Sent Events · Socket.io ที่เขียนเอง |
| **ถ้าเปลี่ยนเป็น polling** | ทำได้และโค้ดง่ายกว่า (หน้า `/q/:token` ใช้วิธีนี้อยู่จริง — poll ทุก 15 วินาที เพราะ role `anon` ไม่มี policy บน `queue_tickets` จึงรับ event ไม่ได้) แต่จอครัวที่ poll ทุก 15 วินาทีหมายถึงอาหารอาจขึ้นช้าถึง 15 วินาที ซึ่งในร้านจริงคือปัญหา · และ 20 จอ × poll ทุก 3 วินาที = 400 request/นาที ซึ่งเปลืองกว่า WebSocket ค้างเดียว |
| **ตาข่ายรับที่ทำไว้** | Realtime ไม่ส่ง event ย้อนหลัง ของที่เปลี่ยนตอนเน็ตหลุดจะหายไปเลย โค้ดจึงดัก event `online` ของเบราว์เซอร์แล้วโหลดใหม่ทั้งชุด และยิง resync ทุกครั้งที่ status เป็น `SUBSCRIBED` |

### 5.8 Authentication — Supabase Auth (2 ชนิดผู้ใช้)

| ชนิด | วิธีเข้า | ตัวชี้ขาดสิทธิ์ |
|---|---|---|
| พนักงาน / ผู้จัดการ | อีเมล + รหัสผ่าน (`signInWithPassword`) | มีแถวใน `profiles` → `is_staff()` / `is_manager()` |
| ลูกค้าที่โต๊ะ | **Anonymous sign-in** (ไม่ต้องสมัคร) | มีแถวใน `visit_devices` ที่ยังไม่ถูก revoke → `current_visit_id()` |
| คนยืนรอหน้าร้าน | ไม่ล็อกอินเลย (role `anon`) | ถือ `public_token` ของบัตรคิว เรียกได้แค่ `get_queue_status()` |

**ประเด็นที่ต้องอธิบายให้ชัด:** ใน Supabase คำว่า `authenticated` **ไม่ได้แปลว่า “พนักงาน”** ลูกค้าที่ `signInAnonymously()` ก็ได้ role `authenticated` เหมือนกัน (ต่างแค่ `is_anonymous = true`) — นี่คือสาเหตุของช่องโหว่ที่ migration `0021` ไปปิด (policy เดิมเขียน `using (true)` ทำให้ใครก็ตามที่สมัคร anonymous เองอ่านตาราง `branches` ได้)

| หัวข้อ | เนื้อหา |
|---|---|
| **ทำไมลูกค้าไม่ต้องสมัคร** | คนมากินชาบูไม่มีใครอยากสมัครสมาชิกก่อนสั่งอาหาร แต่ระบบยังต้องรู้ว่า “เครื่องนี้คือโต๊ะไหน” เพื่อให้ RLS ทำงาน — anonymous sign-in ให้ JWT มาโดยไม่ต้องกรอกอะไร แล้วเอา JWT ไปผูกกับ visit ผ่านตาราง `visit_devices` |
| **ทางเลือกอื่น** | ให้สมัคร/ล็อกอิน (เสียลูกค้า) · ใช้ token ล้วนไม่มี session (`0010`) ซึ่งทำได้แต่**เสีย Realtime**เพราะ `anon` ไม่มี policy บนตาราง · ใช้ session cookie ของ backend ที่เขียนเอง |
| **ข้อเสียที่ต้องยอมรับ** | **บัญชี anonymous งอกขึ้นเรื่อย ๆ** ทุกครั้งที่มีคนเปิดหน้าเว็บ ลบทิ้งยากเพราะ `visit_devices` เป็น CASCADE และ `audit_logs.actor_id` เป็น SET NULL — ต้อง denormalize ก่อนถึงจะลบได้ (บันทึกไว้ในรายการงานค้าง) |
| **ถ้าปิด Anonymous sign-in ไม่ได้** | มีทางสำรองเตรียมไว้แล้วใน `0010_token_fallback.sql` — 4 ฟังก์ชันที่รับ token เป็นพารามิเตอร์แล้วตรวจเอง เปิดให้ role `anon` เรียกได้ ตารางยังปิดสนิท แลกกับการต้อง poll แทน Realtime |

**PGlite คืออะไร และทำไมถึงเลือก**
PGlite คือ PostgreSQL ที่คอมไพล์เป็น WebAssembly รันในหน่วยความจำ ไม่ต้องติดตั้ง Docker ไม่ต้องมีเซิร์ฟเวอร์ ทำให้รันเทสต์ฐานข้อมูลได้ด้วย `node rules.test.mjs` ตัวเดียว

- **ทางเลือกอื่น:** Docker + Postgres จริง (ช้ากว่า ต้องลง Docker) · testcontainers · mock ฐานข้อมูล (ไม่ได้ทดสอบ SQL จริงเลย)
- **ข้อจำกัดที่ต้องพูดตามจริง:** PGlite ต่อได้ทีละ connection จึง **จำลอง race condition ไม่ได้** เป็นเหตุผลที่ต้องมี `concurrency.test.mjs` แยกไปยิง Postgres จริง · และ PGlite ไม่มี Supabase Storage จึงต้อง stub schema `storage` เอง แปลว่า **policy 4 ตัวบน `storage.objects` ยังไม่เคยถูกทดสอบจริง**

**ทำไมต้องมี Playwright ทั้งที่ PGlite ผ่านหมดแล้ว**
ตรวจพบเหตุผลเขียนไว้ใน `e2e/playwright.config.js` — เคยมีบั๊กคิดเงินเด็กเป็นผู้ใหญ่ที่ **รอดจากเทสต์ฐานข้อมูลทั้งหมด** เพราะเทสต์เรียก `open_visit()` ด้วยค่าที่ถูกอยู่แล้ว ส่วนหน้าจอส่ง `party_size` เป็นผู้ใหญ่ล้วน ชั้นที่ขาดคือ “หน้าจอส่งอะไรเข้า RPC” ซึ่งต้องกดผ่าน UI จริงเท่านั้นถึงเห็น — **นี่คือคำตอบชั้นดีสำหรับคำถามว่าทำไมต้องมีเทสต์หลายชั้น**

## 6. Architecture

### ภาพรวม — 3 ชั้น ไม่มี backend server แยก

```
┌─────────────────────────────────────────────────────────┐
│  Browser  (React 19 SPA · โฮสต์บน Vercel · static ล้วน) │
│    ลูกค้า · พนักงาน · ครัว · ผู้จัดการ · จอคิว              │
└───────┬──────────────┬──────────────┬───────────────────┘
        │ HTTPS        │ HTTPS        │ WebSocket
        │ select       │ POST /rpc/*  │ postgres_changes
        ▼              ▼              ▼
┌─────────────────────────────────────────────────────────┐
│  Supabase                                               │
│   PostgREST  │  Auth (JWT)  │  Realtime  │  Storage     │
└───────────────────────┬─────────────────────────────────┘
                        ▼
┌─────────────────────────────────────────────────────────┐
│  PostgreSQL — ตรรกะธุรกิจทั้งหมดอยู่ที่นี่                  │
│   28 ตาราง · 1 view · 42 function · 26 trigger          │
│   54 RLS policy · 61 CHECK · 57 FK · 37 index           │
└─────────────────────────────────────────────────────────┘
```

### คำถามอาจารย์: “ทำไมแบ่งแบบนี้ รวมเป็นระบบเดียวได้ไหม”

**คำตอบ:** ระบบนี้**รวมเป็นระบบเดียวอยู่แล้ว** — ไม่มี microservice ไม่มี backend server แยก มีแค่ frontend กับฐานข้อมูล การตัดสินใจจริงคือ “จะวางตรรกะไว้ที่ไหน” ซึ่งเลือกวางไว้ที่ฐานข้อมูลด้วยเหตุผลข้อเดียว

> จุดที่ข้อมูลจะพังคือจุดที่มีทางเข้าหลายทาง ระบบนี้มีคนเข้าถึงข้อมูลเดียวกัน 4 ทาง — ลูกค้าสแกน QR, พนักงานหน้าร้าน, จอครัว, หน้าผู้จัดการ ถ้าเขียนกฎ “ห้ามเก็บเงินเกินยอดบิล” ไว้ที่ backend ต้องเขียนซ้ำทุกทางเข้า ลืมทางใดทางหนึ่งเงินก็ผิด พอย้ายกฎลงไปอยู่ในฐานข้อมูล กฎมีที่เดียว ทุกทางเข้าถูกบังคับเหมือนกันหมด

### ข้อดี–ข้อเสียของสถาปัตยกรรมนี้

| ข้อดี | ข้อเสีย |
|---|---|
| กฎมีที่เดียว เพิ่มแอปมือถือไม่ต้องเขียนกฎใหม่ | ตรรกะอยู่ใน SQL ทำให้ทำ code review และ version control ยากกว่า |
| ได้ transaction ฟรี — `close_visit` แก้ 5 ตารางพร้อมกัน สำเร็จทั้งหมดหรือไม่เกิดอะไรเลย | ไม่มีที่วางงานที่ไม่ใช่ฐานข้อมูล เช่นส่ง LINE/อีเมล ต้องไปทำเป็น Edge Function เพิ่ม |
| ไม่มีเซิร์ฟเวอร์ให้ดูแล ค่าใช้จ่ายเป็นศูนย์ในระดับนี้ | ผูกกับ Supabase ในส่วน Auth/Realtime |
| frontend เป็น static ล้วน → scale ด้วย CDN ได้ทันที | ทุก request วิ่งเข้าฐานข้อมูลตรง ไม่มีชั้น cache คั่น |

### ถ้าเปลี่ยนเป็นสถาปัตยกรรมอื่นจะเกิดอะไร

| เปลี่ยนเป็น | ผลที่เกิด |
|---|---|
| **3-tier มี backend server** | ควบคุมได้มากขึ้น วาง cache และงานพื้นหลังได้ แต่ต้องเขียน endpoint ~30 ตัว, ทำ WebSocket เอง, และยังต้องกันคนยิงฐานข้อมูลตรงอยู่ดี — งานเพิ่มหลายเท่า |
| **Microservice** | ผิดขนาดปัญหาอย่างชัดเจน ระบบร้านเดียว 28 ตาราง แยกเป็น service แล้วจะได้ปัญหา distributed transaction แทน — ตอนนี้ `close_visit` แก้ 5 ตารางใน transaction เดียวจบ แยก service เมื่อไหร่ต้องทำ saga pattern ทันที |
| **Serverless function คั่นกลาง** | เพิ่ม cold start และเพิ่มจุดที่ต้อง deploy โดยที่กฎยังต้องอยู่ที่ฐานข้อมูลอยู่ดี |

### 7.3 View — `public_settings`

มี view เดียวในระบบ แก้ปัญหาที่ตรงจุดมาก

**ปัญหา:** `restaurant_settings` มีข้อมูลอ่อนไหว (`promptpay_id`, `tax_id`, `legal_name`) ที่ไม่ควรหลุดไปอยู่ในเบราว์เซอร์ลูกค้า แต่ลูกค้าก็ต้องอ่านค่าอย่างเพดานการสั่งและอัตรา VAT เพื่อแสดงผล
**และ RLS จำกัดได้เป็นแถว ไม่ใช่คอลัมน์**

**ทางแก้:** สร้าง view ที่เลือกเฉพาะ 19 คอลัมน์ที่ปลอดภัย แล้ว `grant select on public_settings to authenticated` — view ไม่ได้ตั้ง `security_invoker` จึงรันด้วยสิทธิ์เจ้าของ = ข้าม RLS ของตารางต้นทางได้ ทำให้ตารางจริงยังปิดสนิทอยู่

> **นี่คือคำตอบของคำถาม “RLS ทำ column-level security ได้ไหม”** — ตอบว่าไม่ได้ แล้วโชว์ว่าแก้ด้วย view

### 7.4 คำถามอาจารย์เรื่องการออกแบบฐานข้อมูล

**Q: ทำไมต้องมี Primary Key / Foreign Key / Index / Constraint**

- **PK** — ทุกตารางใช้ `uuid` ที่ `gen_random_uuid()` สร้าง ยกเว้นตาราง log ที่ใช้ `bigserial` และตารางเชื่อมที่ใช้ composite key เลือก uuid เพราะ **ระบบมีหลายเครื่องเขียนพร้อมกัน** ถ้าใช้ auto-increment ต้องรอฐานข้อมูลออกเลขให้ทีละใบ และเลขเดาได้ (ยิง `/visits/1` ต่อ `/visits/2` ได้)
- **FK** — มี 57 จุด บังคับว่าออเดอร์ต้องชี้ไป visit ที่มีอยู่จริง ใช้ `on delete` ต่างกันตามความหมาย: `cascade` (ลบ visit แล้วออเดอร์ควรหายด้วย) · `restrict` (ห้ามลบเมนูที่เคยถูกสั่ง) · `set null` (ลบพนักงานแล้ว audit log ยังอยู่แต่ไม่รู้ว่าใคร)
- **Index** — มี `create index` ที่เขียนเอง **37 คำสั่ง** (รวมกับ index ที่ PostgreSQL สร้างให้อัตโนมัติจาก PK/unique จะเป็น **79 ตัว**) ออกแบบตาม query ที่ใช้จริง
- **CHECK constraint** — มี **61 ตัว** บังคับกฎที่เป็นความจริงเสมอ เช่น จำนวนคน ≥ 1, เงินทอนต้องเท่ากับเงินที่ยื่นลบยอดที่ต้องจ่าย

**Q: รวมตารางได้ไหม เช่นเอา `order_items` ไปไว้ใน `orders` เป็น jsonb**

ได้ในทางเทคนิค แต่จะเสียสามอย่างทันที

1. **สถานะรายจานหายไป** — จอครัวต้องกรอง “จานที่ยังไม่เสร็จของสถานีเนื้อ” ซึ่ง index บน `(station_id, status, created_at)` ทำได้เร็ว แต่ถ้าอยู่ใน jsonb ต้องอ่านทุกแถวมาแกะ
2. **FK ไป `menu_items` หายไป** — ลบเมนูแล้วประวัติการสั่งจะชี้ไปของที่ไม่มีอยู่
3. **`order_status_history` ผูกไม่ได้** — ต้องเก็บประวัติเป็น array ซ้อนใน jsonb ซึ่งเขียนพร้อมกันหลายคนแล้วทับกัน

**Q: `visits` เก็บ snapshot ราคาซ้ำกับ `buffet_packages` ผิด 3NF หรือเปล่า**

> **เป็นคำถามที่อาจารย์วิชาฐานข้อมูลน่าจะถามที่สุด — เตรียมคำตอบนี้ให้แม่น**

ผิดตามนิยามของ 3NF จริง แต่เป็นการ **denormalize โดยเจตนา** ด้วยเหตุผลที่ต่างจากการ denormalize เพื่อ performance ทั่วไป

- ค่าใน `buffet_packages.price_per_adult_satang` คือ **ราคาปัจจุบัน** ซึ่งเปลี่ยนได้
- ค่าใน `visits.package_price_adult_satang` คือ **ราคา ณ เวลาที่เกิดธุรกรรม** ซึ่งต้องไม่เปลี่ยนตลอดกาล
- **สองค่านี้มีความหมายคนละอย่าง ไม่ใช่ข้อมูลซ้ำ** ถ้าเก็บอย่างเดียวแล้ว JOIN เอา ร้านขึ้นราคาเมื่อไหร่ บิลเก่าทุกใบจะเปลี่ยนยอดย้อนหลังทันที ซึ่งผิดทั้งทางบัญชีและทางกฎหมาย
- หลักการเดียวกันนี้ใช้กับ `order_items.name_snapshot`, `visit_addons.unit_price_satang`, `visit_promotions.name_snapshot` และทั้งตาราง `bill_lines`

**ประโยคสรุปที่ใช้ตอบได้เลย:** “Normalization ใช้กับข้อมูลอ้างอิง (master data) ส่วนข้อมูลธุรกรรม (transactional data) ต้องเก็บ snapshot เพราะมันบันทึกความจริง ณ เวลาหนึ่ง ไม่ใช่สถานะปัจจุบัน”

## 9. Function / Logic สำคัญ

### 9.1 `next_counter()` — กันเลขคิวและเลขใบเสร็จซ้ำ

```sql
insert into daily_counters (branch_id, counter_key, counter_date, current_value)
values (p_branch_id, p_key, v_date, 1)
on conflict (branch_id, counter_key, counter_date)
do update set current_value = daily_counters.current_value + 1
returning current_value into v_value;
```

**ทำงานอย่างไร:** คำสั่งเดียวจบ ไม่มีช่วง “อ่านแล้วค่อยเขียน” ให้ใครแทรก PostgreSQL ล็อกแถวให้เองตอนทำ `ON CONFLICT DO UPDATE`
**ทำไมไม่ใช้ `SEQUENCE`:** เพราะต้อง **รีเซ็ตทุกวันและแยกตามสาขา** ซึ่ง sequence ทำไม่ได้ ที่นี่ `counter_date` เป็นส่วนหนึ่งของ primary key พอขึ้นวันใหม่ก็เป็นแถวใหม่ที่เริ่มจาก 1 เอง
**ทำไมไม่ทำใน JavaScript:** `SELECT max(ticket_number)+1` แล้วค่อย INSERT มีช่องว่างให้อีกเครื่องอ่านค่าเดียวกันได้ → เลขคิวซ้ำ
**อีกชั้นที่กันไว้:** `unique (branch_id, ticket_date, ticket_number)` บนตาราง `queue_tickets` — ต่อให้ตรรกะพลาด ฐานข้อมูลก็ยังปฏิเสธ

### 9.2 `recalculate_visit_totals()` — คิดเงินทั้งบิล

ไฟล์ `0008_functions_rpc.sql` — ฟังก์ชันที่ควรใช้เป็นสไลด์หลัก

```
1. SELECT ... FOR UPDATE ล็อกแถว visit
2. DELETE bill_lines เดิมทิ้งทั้งชุด แล้วสร้างใหม่
3. ค่าบุฟเฟต์ = adult_count × ราคาผู้ใหญ่(snapshot) + child_count × ราคาเด็ก(snapshot)
4. + add-on จาก visit_addons
5. + อาหารสั่งพิเศษ (JOIN + GROUP BY ดูหมวด 10)
6. − ส่วนลด โดยจำกัดด้วย least(discount, subtotal) กันลดจนติดลบ
7. + service charge ตามอัตราใน restaurant_settings
8. + VAT แยกสองกรณี inclusive / exclusive
9. UPDATE visits ด้วยยอดทั้ง 5 ตัว
```

**สามอย่างที่ต้องชี้ให้เห็น**

1. **ไม่มีเลข 299 / 399 / 39 ในฟังก์ชันนี้เลย** ทุกค่ามาจาก snapshot ในแถวและจากตารางตั้งค่า
2. **VAT แบบ inclusive คำนวณต่างจาก exclusive** — inclusive ต้องถอดภาษีออกจากยอดที่รวมแล้วด้วยสูตร `total × rate / (10000 + rate)` ไม่ใช่คูณตรง ๆ
3. **อัตราเก็บเป็น basis point** (700 = 7.00%) เพราะเก็บเป็นทศนิยมแล้วปัดเศษจะเพี้ยน

### 9.4 `close_visit()` — transaction ที่แก้ 5 ตารางพร้อมกัน

```
visits            → status='closed', session_token=null, access_code=null
visit_devices     → revoked_at = now()  (ทุกเครื่องของโต๊ะนี้)
```

**ถ้าพังกลางทาง จะไม่เกิดอะไรขึ้นเลย** — นี่คือค่าของ transaction ถ้าแยกเป็น API 5 ตัวแล้วตัวที่ 3 ล้ม จะได้โต๊ะที่ปิดแล้วแต่ QR ยังใช้ได้

### 9.5 State machine 3 ตัว

| อะไร | เส้นทางที่อนุญาต | บังคับด้วย |
|---|---|---|
| โต๊ะ | `available → occupied → cleaning → available` (+ `reserved`, `disabled`) | trigger `enforce_table_status_transition` |
| รอบบริการ | `open → awaiting_payment → paid → closed` (+ `void` ที่ต้องมีเหตุผล) | trigger `enforce_visit_status_transition` |
| รายจาน | `pending → preparing → ready → served` (ถอยกลับได้บางขา) | เงื่อนไขใน `advance_order_item()` |

**ทำไมต้องบังคับที่ฐานข้อมูล ไม่ใช่ซ่อนปุ่มใน UI:** เพราะปุ่มที่ซ่อนไว้ยังยิง API ได้อยู่ และมีหลายหน้าจอที่แก้สถานะเดียวกัน

**สองการตัดสินใจที่ควรอธิบาย**

- **ทำไม `paid` กับ `closed` ต้องแยก:** ลูกค้าจ่ายเงินแล้วยังนั่งคุยต่อได้อีกครึ่งชั่วโมง ถ้ารวมเป็นสถานะเดียว โต๊ะจะถูกปล่อยให้คิวถัดไปทันทีทั้งที่ยังมีคนนั่งอยู่
- **ทำไมโต๊ะต้องผ่าน `cleaning`:** ถ้าปิดรอบแล้วโต๊ะว่างทันที ระบบจะจัดคิวถัดไปลงโต๊ะที่ยังไม่ได้เช็ด

### 9.6 `rollup_order_status()` — trigger ที่คำนวณสถานะใบแม่

```sql
case when count(*) filter (where status <> 'cancelled') = 0 then 'cancelled'
     when count(*) filter (where status = 'pending')    > 0 then 'pending'
     when count(*) filter (where status = 'preparing')  > 0 then 'preparing'
     when count(*) filter (where status = 'ready')      > 0 then 'ready'
     else 'served' end
```

`orders.status` = ความคืบหน้าที่ **ช้าที่สุด** ในบรรดาจานที่ยังไม่ถูกยกเลิก — ใช้ `FILTER` clause ของ PostgreSQL ซึ่งอ่านง่ายกว่า `CASE` ซ้อนใน `SUM()`

### 9.7 `visit_amount_due()` — บทเรียนเรื่อง NULL ที่เล่าได้ดีมาก

> **ถ้าเหลือเวลาถาม-ตอบ เรื่องนี้คือเรื่องที่ควรเล่า** เพราะมันแสดงว่าเข้าใจ three-valued logic ของ SQL จริง

migration `0018` ใส่ด่านตรวจสิทธิ์ไว้แบบนี้

```sql
if not (is_staff() or p_visit_id = current_visit_id()) then raise ...
```

ดูเหมือนถูก แต่สำหรับคนที่ไม่ได้ล็อกอิน `current_visit_id()` คืน `null`

```
is_staff()                = false
p_visit_id = null         = null      ← ไม่ใช่ false
false or null             = null
not null                  = null
if null then              = ไม่เข้าเงื่อนไข
```

**ผลคือด่านไม่เคยทำงานเลยสำหรับคนที่ควรถูกกันมากที่สุด** ทดสอบแล้วยังได้ 200 ตามเดิม

migration `0019` แก้ด้วย `coalesce` ครอบทั้งก้อน

```sql
if not coalesce(is_staff() or p_visit_id = current_visit_id(), false) then raise ...
```

และ migration `0020` พบว่า `visit_amount_reserved()` ซึ่งอ่านตารางเดียวกันด้วยเงื่อนไขกว้างกว่า **ถูกมองข้ามไป** — ยิงทดสอบผ่านอินเทอร์เน็ตจริงแล้วได้ยอดเงินกลับมาจริง

**บทเรียน 3 ข้อจากเรื่องนี้:** ① SQL มี 3 ค่า ไม่ใช่ 2 ② แก้ช่องโหว่แล้วต้องไล่ดูฟังก์ชันพี่น้องที่อ่านข้อมูลเดียวกันด้วย ③ ต้องทดสอบจากมุมคนนอกจริง ไม่ใช่แค่อ่านโค้ดแล้วเชื่อว่าถูก

## 10. Query สำคัญ

### 10.1 Query ที่ซับซ้อนที่สุด — รวมรายการอาหารสั่งพิเศษเข้าบิล

อยู่ใน `recalculate_visit_totals()`

```sql
select oi.name_snapshot,
       sum(oi.quantity)          as qty,
       max(oi.unit_price_satang) as price,
       sum(oi.line_total_satang) as total
from order_items oi
join orders o on o.id = oi.order_id
where o.visit_id = p_visit_id
  and not oi.is_buffet_included
  and oi.status <> 'cancelled'
group by oi.name_snapshot
```

**Query นี้ทำอะไร:** โต๊ะหนึ่งสั่ง 5 รอบ แต่ละรอบมีเนื้อวากิวรอบละ 1 จาน บิลต้องขึ้นบรรทัดเดียวว่า “เนื้อวากิว × 5” ไม่ใช่ 5 บรรทัด

**ทำไมเขียนแบบนี้**

| ส่วน | เหตุผล |
|---|---|
| `join orders` | `order_items` ไม่มี `visit_id` ตรง ๆ ต้องผ่าน `orders` ซึ่งเป็นการ normalize ที่ถูกต้อง |
| `group by name_snapshot` | จัดกลุ่มด้วย **ชื่อที่ snapshot ไว้** ไม่ใช่ `menu_item_id` เพราะถ้าเมนูถูกเปลี่ยนชื่อกลางรอบ บิลต้องแยกบรรทัดตามชื่อที่ลูกค้าเห็นตอนสั่ง |
| `max(unit_price)` | ราคาต่อหน่วยเท่ากันทุกแถวในกลุ่มอยู่แล้ว แต่ SQL บังคับว่าคอลัมน์ที่ไม่ได้ group ต้องผ่าน aggregate — เลือก `max` เพราะสื่อความหมายว่า “หยิบค่ามาหนึ่งตัว” |
| `status <> 'cancelled'` | จานที่ครัวยกเลิกต้องไม่เข้าบิล |

**เขียนอีกแบบได้ไหม:** ได้ เช่นใช้ window function หรือ CTE แต่ผลลัพธ์เหมือนกันและไม่ได้เร็วขึ้น
**ผลต่อ performance:** มี index `idx_order_items_order on order_items(order_id)` และ `idx_orders_visit on orders(visit_id, order_number)` ทำให้ query นี้อ่านเฉพาะแถวของ visit นั้น ไม่ scan ทั้งตาราง

### 10.2 Query ที่ควรยกเป็นตัวอย่างของ “ทำผิดแล้วแก้”

**เวอร์ชันเดิม (ผิด):**
```js
supabase.from('order_items').select('*')     // ดึงทั้งตาราง แล้วมากรองในเบราว์เซอร์
```

**เวอร์ชันปัจจุบัน (ถูก):**
```js
const visitIds = visits.map(v => v.id)
const orders   = await supabase.from('orders').select('*').in('visit_id', visitIds)
const orderIds = orders.data.map(o => o.id)
const items    = await supabase.from('order_items').select('*').in('order_id', orderIds)
```

**ทำไมต้องยิง 3 จังหวะแทนจังหวะเดียว:** เพราะต้องรู้ id ของรอบที่ยังไม่ปิดก่อนถึงจะกรองได้ — ยอมยิงเพิ่ม 2 ครั้งเพื่อให้ไม่ชนเพดาน 1,000 แถวของ PostgREST (ดูหมวด 11)

### 10.3 Query นับคิวที่อยู่ข้างหน้า

```sql
select count(*) from queue_tickets q
 where q.branch_id   = v_row.branch_id
   and q.ticket_date = v_row.ticket_date
   and q.status in ('waiting','called')
   and q.ticket_number < v_row.ticket_number;
```

ตรงกับ index `idx_queue_tickets_waiting on queue_tickets(branch_id, ticket_date, ticket_number) where status in ('waiting','called')` — **partial index ที่คอลัมน์เรียงตรงกับเงื่อนไข query พอดี** ใช้เป็นตัวอย่างของการออกแบบ index ตาม query จริง ไม่ใช่ใส่มั่ว

### 11.1 Index — 37 คำสั่งที่เขียนเอง (79 ตัวเมื่อรวมที่ PostgreSQL สร้างให้)

| index | รองรับ query อะไร |

| `idx_queue_tickets_waiting(branch_id, ticket_date, ticket_number)` บางส่วน | เรียงคิวรายวัน |

**Partial index คืออะไรและทำไมถึงใช้:** `where status in ('waiting','called')` ทำให้ index เก็บเฉพาะแถวที่ยังมีความหมาย บัตรคิวที่จัดโต๊ะไปแล้วไม่ต้องอยู่ใน index — index เล็กลง ค้นเร็วขึ้น และ insert ถูกลงเพราะไม่ต้องอัปเดต index ที่ไม่เกี่ยว

### 11.2 คำถาม “ถ้ามีข้อมูล 1,000 / 100,000 / 1,000,000 รายการจะเกิดอะไรขึ้น”

> **เตรียมคำตอบนี้ให้ดี เพราะชื่อวิชาคือ “การจัดการฐานข้อมูลขนาดใหญ่”**

| ปริมาณ | เกิดอะไร | รับมืออย่างไร |
|---|---|---|
| **1,000 แถว** | **เจอปัญหาจริงแล้ว** — PostgREST ตัดผลลัพธ์ที่ 1,000 แถวโดยไม่แจ้ง error โค้ดเดิมดึง `order_items` ทั้งตารางมากรองในเบราว์เซอร์ พอร้านสั่งครบ 1,000 รายการ ตั๋วที่เพิ่งสั่งจะหายจากจอครัวเงียบ ๆ | ย้ายการกรองลงไปทำที่ฐานข้อมูล กรองด้วย `visit_id` เสมอ · มี `e2e/specs/scale.spec.js` ถมข้อมูล 1,200 แถวเพื่อพิสูจน์ว่าแก้ได้จริง |
| **100,000 แถว** | Query ที่มี index รองรับยังเร็วเหมือนเดิมเพราะ B-tree เป็น O(log n) · แต่หน้าผู้จัดการที่ `select * ... limit 200` จะเริ่มช้าถ้าไม่มี index บนคอลัมน์ที่ใช้เรียง | ใส่ index ตามที่ทำไว้แล้ว · ทำ pagination จริงแทน `limit` ตายตัว |
| **1,000,000 แถวขึ้นไป** | ตารางที่โตไม่หยุดคือ `order_items`, `audit_logs`, `visit_access_attempts` · `audit_logs` เป็น `bigserial` + `jsonb` จะกินพื้นที่มากที่สุด | **Partition ตามเดือน** (PostgreSQL รองรับในตัว) · ย้ายข้อมูลเก่าไป archive · ปัจจุบัน `audit_logs` มี index บน `(branch_id, created_at desc)` อยู่แล้วซึ่งเป็น partition key ที่เหมาะพอดี |

**บั๊ก performance ที่เจอตอนเขียนเทสต์ — เล่าได้ดีมาก**

`order_items` มี trigger `AFTER INSERT` สองตัวที่ทำงาน **ทีละแถว** ตัวหนึ่งไปอัปเดตแถวแม่ใน `orders` ถ้ายัด 400 แถวใส่ออเดอร์ใบเดียว = อัปเดตแถวเดิมซ้ำ 400 ครั้งติดกัน แล้วชน statement timeout
**บทเรียน:** trigger `FOR EACH ROW` สะดวกแต่ไม่เหมาะกับการเขียนทีละเยอะ ถ้าต้องรองรับ bulk insert จริงต้องเปลี่ยนเป็น `FOR EACH STATEMENT` หรือคำนวณ rollup ตอนอ่านแทน

### 11.3 การวัดจริงที่มีเตรียมไว้

`e2e/specs/soak.spec.js` — เปิด 15 โต๊ะพร้อมกัน แต่ละโต๊ะสั่ง 5 รอบ รอบละ 4 รายการ แล้ว**วัดเวลาเป็น percentile** ไม่ใช่ตัดสินผ่าน/ไม่ผ่าน

## 12. Security

### 12.1 ชั้นป้องกันทั้งหมด

| ชั้น | ทำอะไร | ถ้าไม่มีจะเกิดอะไร |
|---|---|---|
| **Authentication** | JWT จาก Supabase Auth ทุก request | ใครก็ยิง API ได้ |
| **RLS** 54 policy | กรองแถวที่ผู้ใช้แต่ละคนเห็นได้ | ลูกค้าโต๊ะ 1 อ่านบิลโต๊ะ 2 ได้ · พนักงานสาขา A อ่านข้อมูลสาขา B ได้ |
| **RPC + `security definer`** | รวมกฎไว้ที่เดียว ทุกทางเข้าบังคับเหมือนกัน | กฎอยู่ใน UI แล้วข้ามได้ด้วย DevTools |
| **CHECK constraint** 61 ตัว | กฎที่จริงเสมอ | ข้อมูลขัดแย้งเข้าตารางได้ เช่นของในบุฟเฟต์มีราคา |
| **Trigger** 26 ตัว | กฎที่ต้องดูหลายแถว | เก็บเงินเกินยอดบิลได้ · สถานะข้ามขั้นได้ |

| **`audit_logs`** | ตรวจย้อนหลังได้ | ตอบไม่ได้ว่าใครยกเลิกบิล |
| **Rate limit** | เพดานการลองรหัส QR, หน่วงเวลาระหว่างออเดอร์, เพดานอุปกรณ์ต่อโต๊ะ | เดารหัส 6 หลักได้ไม่จำกัด · กดสั่งรัวจนท่วมครัว |

### 12.2 การ์ดสำคัญที่เขียนไว้ในโค้ด

**① กันเอา `service_role` key มาใส่ frontend** — `api/supabaseClient.js` อ่าน role ออกจาก JWT payload แล้ว **`throw` ทันที** ถ้าเจอ `service_role`

```js
if (isConfigured && readKeyRole() === 'service_role') {
  throw new Error('อันตราย: กำลังใช้ service_role key ในฝั่ง frontend...')
}
```

> key ตัวนี้ข้าม RLS ได้ทั้งหมดและจะถูก bundle ลงไปใน JS ที่ลูกค้าทุกคนเปิดอ่านได้ — **เลือก throw ไม่ใช่แค่ warn เพราะถ้าแค่เตือน คนจะข้ามไป**
> และมีขั้นตอนตรวจบังคับไว้ในแผนงาน: ทุกครั้งที่ deploy ต้องแกะ bundle ดูว่า JWT ยังเป็น `role":"anon"` อยู่

**② ปิดประตู `anon` ทั้งหมด** — `0009` สั่ง `revoke all on all tables in schema public from anon` แล้วค่อยเปิดเฉพาะฟังก์ชันที่ตั้งใจให้เรียก (`get_queue_status`, และ 4 ฟังก์ชันทางสำรองใน `0010`)

**③ ต้อง `revoke` จาก `PUBLIC` ด้วย ไม่ใช่แค่ `anon`/`authenticated`** — PostgreSQL ให้สิทธิ์ `EXECUTE` กับ `PUBLIC` เป็นค่าเริ่มต้นตอน `create function` การ revoke เฉพาะ role ที่รู้จักจึงไม่พอ สิทธิ์ยังตกทอดผ่าน `PUBLIC` อยู่ (บทเรียนจาก `0013` และ `0019`)

**④ ปุ่ม “ของหมด” ต้องเป็น RPC แยก** — เพราะ RLS จำกัดได้เป็นแถว ไม่ใช่คอลัมน์ ถ้าให้ policy `UPDATE` กับพนักงานตรง ๆ เขาจะแก้ราคาเมนูได้ด้วย จึงเปิดทางเดียวผ่าน `set_menu_item_availability()` ที่แตะได้เฉพาะ `is_available`

### 12.3 คำถาม “ทำไมต้อง Validation / Authentication / Authorization”

| อย่าง | ระบบนี้ทำที่ไหน | ถ้าไม่ทำ |
|---|---|---|
| **Validation** | CHECK constraint 61 ตัว + การตรวจในทุก RPC | ข้อมูลเพี้ยนเข้าตาราง เช่นเงินทอนไม่ตรงกับเงินที่ยื่น หรือโต๊ะที่มี 0 คน |
| **Authentication** | Supabase Auth · ทุก request ต้องมี JWT | ไม่รู้ว่าใครเป็นใคร RLS ทำงานไม่ได้ |
| **Authorization** | `is_staff()` / `is_manager()` / `current_visit_id()` ใน RLS และในทุก RPC | ลูกค้าเปิดบิลโต๊ะอื่น · พนักงานทั่วไปแก้ตั้งค่าร้านหรือยกเลิกบิลได้ |

**ประโยคที่ใช้ปิดคำถามนี้:** “Validation ที่อยู่แค่ในหน้าเว็บคือการช่วยให้ผู้ใช้กรอกถูก ไม่ใช่ระบบความปลอดภัย เพราะเปิด DevTools แล้วข้ามได้หมด ของจริงต้องอยู่ที่ฐานข้อมูลซึ่งข้ามไม่ได้”

| 1 | ทำไมเลือก PostgreSQL | เพราะข้อมูลที่ผิดไม่ได้คือเรื่องเงิน ต้องการฐานข้อมูลที่บังคับความถูกต้องได้ด้วยตัวเอง — ได้ ACID, FK, CHECK, ENUM แบบ type จริง, `jsonb` และที่สำคัญที่สุดคือ **RLS** ซึ่งเป็นตัวที่ทำให้ไม่ต้องมี backend server แยก |
| 2 | ทำไมเลือก Supabase ไม่ใช่ Firebase | Supabase เป็น PostgreSQL ตัวจริง ยังใช้ SQL, trigger, stored procedure และ transaction ข้ามหลายตารางได้ · Firestore เป็น NoSQL ที่ทำ `close_visit` ซึ่งแก้ 5 ตารางพร้อมกันไม่ได้ในท่าเดียวกัน |
| 3 | ทำไมไม่เขียน backend เอง | ระบบมีทางเข้าข้อมูลเดียวกัน 4 ทาง กฎที่อยู่ใน backend ต้องเขียนซ้ำทุกทางเข้า ลืมทางใดทางหนึ่งเงินก็ผิด — ย้ายกฎลงฐานข้อมูลแล้วกฎมีที่เดียว บังคับเหมือนกันหมดโดยอัตโนมัติ |
| 4 | ทำไมเลือก React | หน้าจอต้องเปลี่ยนเองเมื่อข้อมูลเปลี่ยน React ผูก state กับ UI ให้โดยไม่ต้องสั่งอัปเดต DOM เอง · และ component แชร์กันได้ทั้ง 4 ฝั่ง |
| 5 | ทำไมเลือก Vite | dev server เร็ว และตั้ง `host: true` ให้มือถือจริงในวง LAN เข้ามาสแกน QR ทดสอบได้ ซึ่งจำเป็นกับโปรเจกต์นี้โดยตรง |
| 6 | ทำไมเงินเป็น integer ไม่ใช่ decimal | `0.1 + 0.2 !== 0.3` ในเลขทศนิยมลอยตัว เก็บเป็นสตางค์ (integer) แล้วคำนวณด้วยจำนวนเต็มตลอด ปัดเศษเฉพาะตอนคิด VAT ด้วย `round()` ครั้งเดียว |
| 7 | ทำไมอัตราภาษีเก็บเป็น basis point | 700 = 7.00% เก็บเป็น integer เพื่อไม่ให้มีทศนิยมในฐานข้อมูลเลย · ถ้าเก็บเป็น `0.07` จะมีปัญหาการปัดเศษเวลาคูณกับยอดใหญ่ |
| 8 | ทำไมใช้ UUID เป็น PK ไม่ใช่ auto-increment | ระบบมีหลายเครื่องเขียนพร้อมกัน UUID สร้างได้เองโดยไม่ต้องรอฐานข้อมูลออกเลข · และเลขเรียงเดาได้ (`/visits/1` แล้วลอง `/visits/2`) |
| 9 | ทำไมต้อง snapshot ราคา | ราคาปัจจุบันกับราคา ณ เวลาที่เกิดธุรกรรมเป็นคนละความหมาย ถ้า JOIN ราคาสด ร้านขึ้นราคาเมื่อไหร่บิลเก่าทุกใบเปลี่ยนยอดย้อนหลังทันที ซึ่งผิดทางบัญชี |
| 10 | ทำไมใช้ PGlite เทสต์ | เป็น PostgreSQL คอมไพล์เป็น WebAssembly รันในหน่วยความจำ ไม่ต้องลง Docker ได้ทดสอบ SQL จริงไม่ใช่ mock |
| 11 | ทำไมมีเทสต์หลายชั้น | เพราะเคยมีบั๊กคิดเงินเด็กเป็นผู้ใหญ่ที่รอดจากเทสต์ฐานข้อมูลทั้งหมด ชั้นที่ขาดคือ “หน้าจอส่งอะไรเข้า RPC” ซึ่งต้องกดผ่าน UI จริงถึงจะเห็น |
| 12 | ทำไมลูกค้าไม่ต้องสมัครสมาชิก | คนมากินชาบูไม่มีใครอยากสมัครก่อนสั่งอาหาร ใช้ anonymous sign-in ได้ JWT มาโดยไม่ต้องกรอกอะไร แล้วผูกกับโต๊ะผ่าน `visit_devices` |
| 13 | ทำไมลูกค้ากดคิวเองไม่ได้ | เลือกให้พนักงานออกบัตรเพราะควบคุมการจัดโต๊ะได้แม่นกว่า ตู้กดเองเป็นส่วนขยายที่ทำต่อได้บน schema เดิม |
| 14 | ทำไม `paid` กับ `closed` แยกกัน | ลูกค้าจ่ายแล้วยังนั่งต่อได้ ถ้ารวมเป็นสถานะเดียวโต๊ะจะถูกปล่อยให้คิวถัดไปทั้งที่ยังมีคนนั่ง |
| 15 | ทำไมโต๊ะต้องผ่าน `cleaning` | ถ้าว่างทันทีระบบจะจัดคิวถัดไปลงโต๊ะที่ยังไม่ได้เช็ด |
| 16 | ทำไมใช้ตารางเชื่อมล็อกเมนู ไม่ใช่คอลัมน์ `min_package_id` | เพราะแพ็กเกจไม่จำเป็นต้องเรียงลำดับราคาเสมอ ตารางเชื่อมรองรับกรณี “เมนูนี้สั่งได้เฉพาะแพ็กเกจ A กับ C” ซึ่งคอลัมน์เดียวทำไม่ได้ |
| 17 | ทำไมไม่ลบแถวเมื่อยกเลิกคิว | เพราะ Realtime ส่ง event DELETE โดยไม่กรอง RLS (payload มีแค่ PK) จึงใช้การเปลี่ยน status แทนการลบเสมอ · และได้ประวัติ no-show ไว้วิเคราะห์ด้วย |
| 18 | ทำไม bucket รูปเมนูเป็น public | หน้าเมนูฝั่งลูกค้าเปิดจากเครื่องที่ไม่ได้ล็อกอินเป็นพนักงาน ถ้าตั้ง private ต้องออก signed URL ทีละรูปทุกครั้งที่โหลดหน้า · รูปอาหารไม่ใช่ข้อมูลที่ต้องกัน แต่ **“ใครอัปโหลดได้” ต้องกัน** จึงคุมที่ฝั่งเขียนด้วย `is_manager()` |
| 19 | ทำไมไม่ใช้ ORM | query ทุกตัวเป็น `supabase-js` หรือ RPC อยู่แล้ว เพิ่ม Prisma/TypeORM จะเป็นชั้นที่แปลง SQL เป็น SQL อีกที |
| 20 | ทำไมมีสาขา (`branches`) ทั้งที่มีร้านเดียว | เพราะการเติม `branch_id` ทีหลังต้องรื้อ FK, index และ RLS ทุกตาราง — ใส่ตั้งแต่ต้นแทบไม่มีต้นทุน |

## 17. คลังคำถามอาจารย์ — “ใช้วิธีอื่นได้ไหม / ถ้าเปลี่ยนจะเกิดอะไร”

| # | คำถาม | คำตอบ |
|---|---|---|
| 1 | ใช้ HTML + JS ธรรมดาแทน React ได้ไหม | ได้สำหรับหน้าง่าย ๆ อย่าง `/display` · แต่หน้าเช็คบิลกับจอครัวต้องอัปเดตหลายจุดพร้อมกันจาก event เดียว ถ้าจัดการ DOM เอง โค้ดจะกลายเป็น `querySelector` + `innerHTML` ที่หาที่ผิดไม่เจอเมื่อสถานะไม่ตรงกัน |
| 2 | ใช้ MySQL แทนได้ไหม | ได้ในแง่เก็บข้อมูล แต่ **เสีย RLS** ซึ่งเป็นแกนของสถาปัตยกรรมนี้ → ต้องเขียน backend server มาเป็นด่านแทนทั้งระบบ · `jsonb` ใน audit log ก็ต้องเปลี่ยนเป็น JSON ที่ query ยากกว่า |
| 3 | ใช้ MongoDB แทนได้ไหม | ได้ถ้ายอมย้ายกฎทั้งหมดขึ้นไปอยู่ในแอป แต่จะเสีย FK, CHECK constraint และ transaction ข้ามหลาย collection ซึ่งเป็นสามอย่างที่ระบบเงินพึ่งพาอยู่ |
| 4 | ใช้ SQLite ได้ไหม | ไม่เหมาะ เพราะเขียนพร้อมกันหลายคนไม่ได้ (ล็อกทั้งไฟล์) แต่ร้านชาบูมีพนักงานกดพร้อมกันตลอด |
| 5 | ถ้าเปลี่ยนจาก Supabase ไป self-host Postgres | ตัวฐานข้อมูลย้ายได้ทั้งก้อน เพราะ migration เป็น SQL มาตรฐาน · แต่ต้องหาของมาแทน 3 อย่าง — PostgREST (มี open source ใช้ได้) · Auth (ต้องเขียนเองหรือใช้ Keycloak) · Realtime (ต้องทำ WebSocket + logical replication เอง) |
| 6 | ใช้ polling แทน Realtime ได้ไหม | ได้ และ **ระบบนี้ใช้อยู่จริงที่หน้า `/q/:token`** (poll ทุก 15 วินาที) เพราะ role `anon` ไม่มี policy บนตาราง · แต่จอครัวที่ poll ทุก 15 วินาที = อาหารขึ้นช้าถึง 15 วินาที และ 20 จอ × poll ทุก 3 วินาที = 400 request/นาที ซึ่งเปลืองกว่า WebSocket ค้างเดียว |
| 7 | ถ้าเอาตรรกะออกจากฐานข้อมูลไปไว้ในแอป | ทดสอบง่ายขึ้นและ version control ดีขึ้น แต่ต้องเขียนกฎซ้ำทุกทางเข้าทั้ง 4 ทาง และต้องปิดไม่ให้ใครยิงฐานข้อมูลตรงได้เลย — ซึ่งขัดกับการที่ frontend เป็น static ล้วน |
| 8 | ถ้าเปลี่ยนไปใช้ Redux / Zustand / TanStack Query | Redux จะได้ boilerplate เพิ่มโดยไม่ได้อะไรกลับ เพราะ state ก้อนเดียว · **TanStack Query เหมาะที่สุดในทางทฤษฎี** เพราะ state ส่วนใหญ่เป็น server state จะได้ cache, retry, invalidate ที่เขียนเองอยู่ตอนนี้แบบฟรี ๆ — เป็นคำตอบที่ดีของ “ถ้าทำใหม่จะเปลี่ยนอะไร” |
| 9 | ถ้าร้านขยายเป็น 10 สาขา | **โครงสร้างรองรับบางส่วน** — `branch_id` มีใน 15 จาก 28 ตาราง และ RLS ถูกล็อกตามสาขาแล้วใน `0012` · แต่ตารางธุรกรรม (`orders`, `payments`) ยังต้อง join ย้อนผ่าน `visits` ทำให้ policy ซับซ้อนและช้าลงเมื่อข้อมูลเยอะ **ถ้าจะทำจริงต้องเติม `branch_id` ให้ครบก่อน** |
| 10 | ถ้ามีผู้ใช้พร้อมกัน 1,000 คน | frontend เป็น static บน CDN จึงไม่เป็นคอขวด · คอขวดอยู่ที่ Supabase — connection pool และจำนวน Realtime channel · ทางแก้: เพิ่ม plan, ใช้ connection pooler (Supabase มีให้), และลดจำนวนตารางที่ subscribe |
| 11 | ถ้าต้องรองรับ offline | ตอนนี้ทำไม่ได้เลย ทุกอย่างต้องต่อฐานข้อมูล · ถ้าจะทำต้องมี local queue ที่เก็บออเดอร์ไว้แล้ว sync ทีหลัง ซึ่งจะเปิดปัญหาใหม่ทันทีว่า “ถ้าสั่งตอน offline แล้วของหมดไปแล้วจะทำยังไง” |
| 12 | ถ้าไม่มี `bill_lines` ใช้คำนวณสดตอนพิมพ์ได้ไหม | ได้ในวันที่พิมพ์ แต่พิมพ์ซ้ำอีกเดือนหลังจากร้านขึ้นราคาหรือเปิด VAT แล้วจะได้ใบเสร็จคนละยอดกับที่เก็บเงินจริง |
| 13 | ถ้าไม่มี `daily_counters` ใช้ `count(*)+1` ได้ไหม | ไม่ได้ เพราะมีช่องว่างระหว่างอ่านกับเขียนให้เครื่องอื่นแทรก → เลขคิวซ้ำ · และถ้ายกเลิกคิวไปบางใบ `count` จะย้อนกลับไปให้เลขที่เคยใช้แล้ว |
| 14 | ถ้าให้หน้าเว็บส่งยอดเงินมาเลย | ลูกค้าเปิด DevTools แก้ค่าแล้วจ่าย 1 บาทได้ · ระบบนี้จึงถาม `visit_amount_due()` จากฐานข้อมูลเสมอ และมี trigger กันอีกชั้น |
| 15 | ใช้ view แทน RLS ได้ไหม | ได้บางส่วน และระบบนี้**ใช้จริงอยู่ 1 ที่** คือ `public_settings` เพื่อแก้ข้อจำกัดที่ RLS ทำ column-level ไม่ได้ · แต่ถ้าใช้ view แทน RLS ทั้งระบบ ต้องสร้าง view ต่อ role ต่อตาราง ซึ่งจะกลายเป็นหลายสิบ view ที่ต้องซิงก์กันเอง |
| 16 | ถ้าเปลี่ยนจาก Vercel ไปโฮสต์ที่อื่น | ย้ายได้ง่ายมาก เพราะ build ออกมาเป็นไฟล์ static ล้วน · ต้องตั้ง rewrite ให้ทุก path คืน `index.html` เหมือนที่ `vercel.json` ทำ ไม่งั้น SPA จะ 404 เมื่อรีเฟรชหน้าลึก |
| 17 | ทำไมไม่ใช้ `SEQUENCE` ออกเลขคิว | เพราะต้องรีเซ็ตทุกวันและแยกตามสาขา ซึ่ง sequence ทำไม่ได้ · `daily_counters` ใส่วันที่เป็นส่วนหนึ่งของ PK ทำให้รีเซ็ตเองโดยอัตโนมัติ |
| 18 | ถ้าเพิ่มแอปมือถือ (React Native) | **ไม่ต้องแก้ฐานข้อมูลเลยสักบรรทัด** เพราะกฎอยู่ใน RPC และ RLS แล้ว แอปใหม่เรียก RPC ชุดเดิมได้ทันที — นี่คือผลตอบแทนที่ชัดที่สุดของการวางตรรกะไว้ที่ฐานข้อมูล |

## ภาคผนวก · แผ่นโกง 10 ประโยคสำหรับท่องก่อนขึ้นสอบ

1. “ระบบจัดคิวและโต๊ะสำหรับร้านชาบูบุฟเฟต์ ครอบตั้งแต่ออกบัตรคิวถึงเก็บโต๊ะ — 28 ตาราง 42 ฟังก์ชัน 54 RLS policy เทสต์ 134 เคสผ่านหมด”
2. “บุฟเฟต์คิดเงินต่อหัว ไม่ใช่ต่อจาน `order_items` จึงไม่ถือราคา ยอดบิลต้องประกอบจาก 3 ตาราง”
3. “ตรรกะธุรกิจอยู่ในฐานข้อมูล ไม่ใช่ในหน้าเว็บ เพราะระบบมีทางเข้าข้อมูลเดียวกัน 4 ทาง”
4. “RLS คือกฎสิทธิ์ที่ติดอยู่กับตาราง ต่อให้ยิง API ตรง ฐานข้อมูลก็ยังกรองแถวให้อยู่ดี”
5. “ราคาถูก snapshot ลง `visits` ตอนเปิดโต๊ะ ร้านขึ้นราคาพรุ่งนี้ บิลเก่ายังถูกต้อง”
6. “เงินเก็บเป็นสตางค์ integer เสมอ เพราะ 0.1 + 0.2 ไม่เท่ากับ 0.3”
7. “`paid` กับ `closed` แยกกัน เพราะลูกค้าจ่ายแล้วยังนั่งต่อได้ · โต๊ะต้องผ่าน `cleaning` ก่อนว่าง”
8. “เลขคิวไม่ซ้ำเพราะ `insert … on conflict do update returning` ซึ่ง Postgres ล็อกแถวให้เอง บวก unique index อีกชั้น”
9. “เจอเพดาน 1,000 แถวของ PostgREST ที่ตัดข้อมูลเงียบ ๆ แก้โดยย้ายการกรองลงฐานข้อมูล และเขียนเทสต์ถม 1,200 แถวพิสูจน์”
10. “ยิง API จริงจากมุมคนนอกแล้วเจอช่องโหว่จริงหนึ่งจุดที่อ่านยอดเงินโต๊ะอื่นได้ ปิดด้วย migration 0020”
